# План независимой проверки инвариантов Cr3dX

## Основание и граница слепоты

План зафиксирован в фазе A по двум разрешённым источникам:

- `docs/cr3dx-spec-v0.4.0-final.md`, редакция v0.4.2;
- публичный интерфейс и поведение ранее принятого `Cr3dXVerifier`.

Исходники `Cr3dXDeals` и `Cr3dXCredit`, их ABI, тесты и пояснения разработчика не использовались.
`Cr3dXReferenceModel.sol` — прямая модель обещанных свойств, а не предполагаемого алгоритма.
`Cr3dXModelHandler.sol` задаёт абстрактные действия; реальные сигнатуры появятся только в адаптере
фазы B.

Найденные противоречия не разрешаются догадкой. INV-3 целиком заблокирован A-01 и A-03, а INV-19 —
A-02; непротиворечивые подмножества всё равно имеют точные оракулы и тестируются. Полные сценарии
находятся в `SPEC_AMBIGUITIES.md`.

## Замороженный разрешительный список ABI для фазы B

Проверяется не наличие «опасных» имён, а отсутствие любого неожиданного публичного изменяющего
состояние селектора. Конструкторы, ошибки, события и функции `view`/`pure` в этот список не входят.

**Cr3dXDeals — разрешены только:**

```solidity
createDeal(address,uint256,uint256,uint64)
applyEvidence(bytes32)
markDefaulted(bytes32)
```

**Cr3dXCredit — разрешена только:**

```solidity
recordOutcome(bytes32,Result) // ABI-кодирование enum уточняется из скомпилированного ABI
```

У `recordOutcome` дополнительно проверяется, что успешный вызов возможен только со стороны Deals.
Любой другой `nonpayable`/`payable` селектор является провалом INV-7. При этом A-04 и A-05
показывают, что сама спецификация, вероятно, сделала allowlist неполным: тест не расширяется под код,
пока спецификация явно не разрешит конфликт.

## Инварианты

### INV-1 — доверенный путь переходов сделки

- **Класс:** свойство переходов, отсутствие привилегий.
- **Проверяемое свойство:** `FINANCED`, `PAID_LATE` и `PAID_ON_TIME` появляются только как следствие
  применения доказательства с `verifierAccepted = true`; `createDeal`, продвижение высоты и
  `markDefaulted` этих статусов сами не создают.
- **Минимальное состояние:** одна сделка `CREATED`; отдельно — `FINANCED` для платёжных статусов.
- **Последовательность:** перебрать все абстрактные действия без регистрации доказательства, затем
  зарегистрировать корректный фандинг/погашение и повторить наблюдение.
- **Наблюдаемый оракул:** каждый статус после `CREATED` имеет причинную метку применённого
  верифицированного факта; для любого `FINANCED` и закрытого статуса
  `fundingThresholdCrossings == 1`; `APPLIED` всегда имеет `verifierAccepted == true`.
- **Негативный контрпример:** публичный вызов или продвижение времени переводит `CREATED` в
  `FINANCED` без появления применённого funding evidence.

### INV-2 — доказательство учитывается не более одного раза

- **Класс:** свойство состояния.
- **Проверяемое свойство:** один `evidenceId` увеличивает суммы и счётчики максимум один раз.
- **Минимальное состояние:** сделка и одно бизнес-применимое доказательство.
- **Последовательность:** зарегистрировать факт, многократно повторить регистрацию и
  `applyEvidence` до и после терминального состояния доказательства.
- **Наблюдаемый оракул:** `appliedCount <= 1`; снимок всех сумм, статусов, счётчиков, резерва и
  экспозиции после первого применения не меняется повтором.
- **Негативный контрпример:** второй вызов с тем же ID повторно увеличивает `fundedAmount` либо
  `repaidAmount`. Revert против no-op не входит в экономический оракул из-за A-06.

### INV-3 — независимость от порядка всех доказательств

- **Класс:** независимость от порядка, метаморфическое свойство.
- **Проверяемое свойство:** для фиксированного мультимножества фактов все перестановки после
  доведения применимых pending-фактов дают одинаковое экономическое состояние.
- **Минимальное состояние:** одна сделка и минимум два факта; для обнаруженного конфликта — три
  частичных фандинга.
- **Последовательность:** воспроизвести перестановки `repayment → funding`/`funding → repayment`,
  частичных погашений и частичных фандингов; затем довести pending до неподвижной точки.
- **Наблюдаемый оракул:** равны статусы evidence, поля Deal, Outcome, счётчики, score, reserve,
  exposure и available limit. Для repayment/funding сравнение после явного `drainPending` заморожено
  отдельно из-за A-03.
- **Негативный контрпример:** `requiredFunding=100`, суммы 60/50/40 дают 110, 100 либо 150 в
  зависимости от порядка. Это уже воспроизводит конфликт A-01; до исправления спецификации полный
  INV-3 не может стать зелёным.

### INV-4 — единственный канонический итог и уточнение только вверх

- **Класс:** свойство состояния, свойство переходов.
- **Проверяемое свойство:** у сделки максимум один текущий Outcome; он равен прямой классификации
  сумм и меняется только `DEFAULTED → PAID_LATE/PAID_ON_TIME` или
  `PAID_LATE → PAID_ON_TIME`.
- **Минимальное состояние:** профинансированная сделка; для каждой дуги — нужные суммы/дефолт.
- **Последовательность:** объявить дефолт, применять поздние и своевременные погашения, включая
  платежи после закрытия.
- **Наблюдаемый оракул:** полный пересчёт: on-time сумма покрывает face → `PAID_ON_TIME`; иначе
  общая сумма покрывает face → `PAID_LATE`; иначе при дефолте → `DEFAULTED`; иначе итога нет.
- **Негативный контрпример:** поздний платёж после `PAID_ON_TIME` понижает итог до `PAID_LATE` либо
  в истории одновременно остаются два канонических итога одной сделки.

### INV-5 — скор из кеша равен полному пересчёту

- **Класс:** арифметика, независимость от порядка, метаморфическое свойство.
- **Проверяемое свойство:** кеш из трёх счётчиков и полный проход по каноническим итогам всегда дают
  одинаковый score; перестановка сделок/исходов его не меняет.
- **Минимальное состояние:** один заёмщик и несколько сделок всех трёх исходов.
- **Последовательность:** записывать и уточнять итоги в разных порядках, включая выход из дефолта;
  строить вторую модель с тем же мультимножеством итогов в обратном порядке.
- **Наблюдаемый оракул:** `raw = int256(500)+25*onTime-50*late-200*defaulted`, один clamp `[300,850]`;
  кеш-счётчики равны полному пересчёту, оба score равны.
- **Негативный контрпример:** пошаговый clamp после каждого исхода или недекрементированный счётчик
  дефолтов после уточнения даёт отличающийся score.

### INV-6 — дробление платежа не повышает скор

- **Класс:** арифметика, метаморфическое свойство.
- **Проверяемое свойство:** замена одного погашения суммой X на несколько погашений с той же общей
  on-time/late классификацией не создаёт более одного итога и не повышает score.
- **Минимальное состояние:** две одинаковые профинансированные сделки в независимых моделях.
- **Последовательность:** первую погасить одним платежом, вторую — частями с той же общей суммой и
  тем же отношением к dueBlock.
- **Наблюдаемый оракул:** один канонический Outcome на сделку, один счётчик, одинаковый score.
- **Негативный контрпример:** каждое частичное погашение увеличивает `paidOnTimeCount` и даёт +25.

### INV-7 — отсутствие привилегированных путей записи

- **Класс:** отсутствие привилегий.
- **Проверяемое свойство:** runtime ABI Deals/Credit не содержит изменяющих состояние функций вне
  замороженного allowlist; роли не могут напрямую писать status/evidence/outcome/reserve/exposure/score.
- **Минимальное состояние:** развёрнутые контракты и адреса деплоера, заёмщика, инвестора, outsider.
- **Последовательность:** извлечь ABI, отфильтровать `nonpayable/payable`, сравнить точное множество
  селекторов; каждый разрешённый селектор вызвать от каждой роли с граничными аргументами.
- **Наблюдаемый оракул:** точное равенство множеств селекторов; `recordOutcome` успешен только от
  Deals; никакая роль не получает прямой переход.
- **Негативный контрпример:** любой неожиданный `emergencySetState`, `setDeals`, `release`, `cancel`,
  `setScore` или вообще селектор с иным именем/сигнатурой. A-04/A-05 требуют решения спецификации,
  а не молчаливого расширения теста.

### INV-8 — происхождение каждого доказательства

- **Класс:** свойство состояния.
- **Проверяемое свойство:** бизнес-модель не имеет способа создать Evidence без факта, записанного
  Verifier после успешной криптографической проверки транзакции и события gateway.
- **Минимальное состояние:** валидный и невалидный пруф одного события.
- **Последовательность:** подать bad proof, failed receipt, чужой emitter и валидный gateway log;
  затем попытаться применить произвольный ID.
- **Наблюдаемый оракул:** только ID, возвращённый/прочитанный из Verifier, появляется в бизнес-модели;
  в эталонной модели единственная точка входа ставит `verifierAccepted=true`.
- **Негативный контрпример:** `applyEvidence` принимает calldata-поля события от вызывающего без
  существующей записи Verifier.

### INV-9 — насыщенный outstanding и точная экспозиция

- **Класс:** арифметика и учёт, свойство состояния.
- **Проверяемое свойство:** `outstanding=max(faceValue-repaidAmount,0)`; exposure заёмщика равна
  полному суммированию outstanding только по `FINANCED` и `DEFAULTED`.
- **Минимальное состояние:** несколько сделок одного заёмщика, включая активную, дефолтную и
  переплаченную закрытую.
- **Последовательность:** финансировать, частично погашать, объявлять дефолт, переплачивать и
  уточнять итог.
- **Наблюдаемый оракул:** независимый проход по списку сделок равен кешу exposure; outstanding
  никогда не underflow; дефолт сам exposure не меняет.
- **Негативный контрпример:** `face=100`, repayment=150 приводит к отрицательному/ревертящему
  outstanding либо дважды уменьшает exposure.

### INV-10 — лимит создания и насыщенный available

- **Класс:** арифметика и учёт, свойство переходов.
- **Проверяемое свойство:** create разрешён iff валидны terms и `faceValue <= availableLimit`, где
  `available = used >= limit ? 0 : limit-used`.
- **Минимальное состояние:** заёмщик с резервом/экспозицией; отдельно — падение score ниже used.
- **Последовательность:** занять лимит, снизить score дефолтом, читать available и создавать сделку
  на `available`, затем на `available+1`.
- **Наблюдаемый оракул:** чтение не ревертит при `used > limit`; точная граница принимается, превышение
  отклоняется без изменения резерва.
- **Негативный контрпример:** обычное `limit-used` underflow при падении score либо создание сверх
  нулевого available.

### INV-11 — применимый фандинг не уничтожается проверками Creditcoin

- **Класс:** свойство переходов.
- **Проверяемое свойство:** корректные investor/recipient до достижения requiredFunding всегда
  применяются независимо от dueBlock, height, limit и ролей; после порога новый funding получает
  только `ALREADY_FUNDED`.
- **Минимальное состояние:** `CREATED`, в том числе просроченная и с исчерпанным текущим лимитом.
- **Последовательность:** подать частичные/полные фандинги до и после порога при разных высотах и
  score; вызывать от разных submitter-адресов.
- **Наблюдаемый оракул:** до порога растёт fundedAmount и состояние `APPLIED`; после порога сумма не
  меняется, состояние `REJECTED_PERMANENT/ALREADY_FUNDED`.
- **Негативный контрпример:** просроченный, недостаточный или «сверх текущего лимита» корректный
  фандинг отклонён. Для перестановок трёх частей действует нерешённый A-01.

### INV-12 — своевременность только по полной on-time сумме

- **Класс:** арифметика, свойство переходов.
- **Проверяемое свойство:** `PAID_ON_TIME` iff сумма применённых погашений с
  `blockHeight <= dueBlock` не меньше faceValue.
- **Минимальное состояние:** профинансированная сделка и платежи по обе стороны dueBlock.
- **Последовательность:** менять порядок поздних/своевременных частей, доставлять своевременный пруф
  после default и после `PAID_LATE`.
- **Наблюдаемый оракул:** прямое суммирование evidence по высоте; момент подачи не участвует.
- **Негативный контрпример:** один своевременный частичный платёж плюс поздний остаток ошибочно дают
  `PAID_ON_TIME`, хотя onTimeRepaid < faceValue.

### INV-13 — резерв переносится в экспозицию один раз

- **Класс:** учёт, свойство переходов.
- **Проверяемое свойство:** create добавляет faceValue в reserve; части до порога его не меняют;
  единственное пересечение порога вычитает faceValue из reserve и добавляет faceValue в exposure.
- **Минимальное состояние:** одна созданная сделка и два частичных фандинга.
- **Последовательность:** создать, применить часть ниже порога, часть через порог, повторный funding,
  default и outcome refinement.
- **Наблюдаемый оракул:** полный пересчёт `reserveActive` равен кешу; crossings <= 1; после порога
  reserve=0 для сделки; default/refinement резерв не трогают.
- **Негативный контрпример:** каждый funding-кусок уменьшает reserve/увеличивает exposure либо
  cancel/default освобождает резерв.

### INV-14 — единственные часы дедлайна

- **Класс:** свойство переходов, метаморфическое свойство.
- **Проверяемое свойство:** default зависит только от аттестованной высоты источника и строгого
  `height > dueBlock+grace`; своевременность — только от evidence.blockHeight.
- **Минимальное состояние:** `FINANCED`, dueBlock и управляемые source/Creditcoin heights.
- **Последовательность:** менять локальные block.number/timestamp при неизменной аттестованной
  высоте; затем продвинуть только source height; доставить старое своевременное погашение поздно.
- **Наблюдаемый оракул:** первые мутации ничего не меняют; строгая граница не дефолтит, следующий
  source block дефолтит; старый blockHeight даёт on-time.
- **Негативный контрпример:** `vm.roll` Creditcoin вызывает default либо поздняя доставка меняет
  своевременный платёж на late.

### INV-15 — непокрытые поля не влияют на состояние

- **Класс:** метаморфическое свойство.
- **Проверяемое свойство:** изменение только `from` или `gasUsed` RPC-обёртки не меняет evidence IDs,
  сохранённые поля и бизнес-состояние.
- **Минимальное состояние:** две эквивалентные доказанные транзакции/декодированные формы с
  одинаковыми покрытыми полями и логами.
- **Последовательность:** подать метаморфическую пару, различающуюся только непокрытыми полями.
- **Наблюдаемый оракул:** равны IDs и все состояния; ABI/декодер не передаёт эти поля в Deals/Credit.
- **Негативный контрпример:** sender берётся из `from`, а не из indexed поля доказанного лога.

### INV-16 — txIndex только после verify того же пруфа

- **Класс:** свойство переходов.
- **Проверяемое свойство:** `calculateTxIndex(mp)` никогда не вызывается до успешного `verify` с тем
  же mp; при revert verify индекс не вычисляется и Evidence не появляется.
- **Минимальное состояние:** инструментированный BlockProver и два различимых proof-объекта.
- **Последовательность:** bad proof; good proof A с попыткой подменить proof B на расчёте индекса.
- **Наблюдаемый оракул:** журнал mock-вызовов строго `verify(A) → calculate(A)`; bad заканчивается
  только `verify`.
- **Негативный контрпример:** `calculate(B)` до `verify(A)` формирует ID из непроверенных siblings.

### INV-17 — все подходящие логи дают ровно по одному Evidence

- **Класс:** свойство состояния.
- **Проверяемое свойство:** число новых evidence равно числу логов с gateway emitter и одним из двух
  topics; порядок IDs соответствует transaction/log order; нерелевантные логи пропускаются.
- **Минимальное состояние:** одна успешная доказанная транзакция с двумя gateway events и одним
  посторонним логом.
- **Последовательность:** подать одиночный proof и batch с такими транзакциями.
- **Наблюдаемый оракул:** два уникальных ID, два `EvidenceRecorded`, разные eventNonce не считаются
  повтором; посторонний лог не создаёт факт.
- **Негативный контрпример:** обработан только первый подходящий лог либо вся транзакция сведена к
  одному evidenceId.

### INV-18 — порог фандинга пересекается один раз

- **Класс:** свойство состояния, свойство переходов.
- **Проверяемое свойство:** `CREATED → FINANCED` и перенос учёта случаются ровно один раз;
  `fundingThresholdCrossings <= 1`; обратного пути нет.
- **Минимальное состояние:** сделка и части, одна из которых пересекает requiredFunding.
- **Последовательность:** части до/через порог, переплата, повторные funding evidence, прочие статусы.
- **Наблюдаемый оракул:** первый crossing фиксирует investor и accounting; все последующие funding
  отклонены `ALREADY_FUNDED` без изменения суммы.
- **Негативный контрпример:** второй funding снова уменьшает reserve или увеличивает exposure.

### INV-19 — полный критерий постоянного отказа

- **Класс:** свойство состояния.
- **Проверяемое свойство:** множество причин строго `{WRONG_INVESTOR, ALREADY_FUNDED,
  WRONG_RECIPIENT}`; первые две только Funding, третья оба вида; permanent iff нет допустимого
  будущего состояния.
- **Минимальное состояние:** unknown deal, CREATED до/после threshold и FINANCED; оба вида evidence.
- **Последовательность:** построить полную таблицу kind × existence × investor-fixed × recipient ×
  designated × threshold; для pending создать состояние, которое должно сделать факт применимым.
- **Наблюдаемый оракул:** независимый existential oracle `canEverBecomeApplicable`; тип причины и
  неизменяемость полей подтверждают permanent; ни одной четвёртой причины.
- **Негативный контрпример:** unknown deal отклонён навсегда или wrong investor висит pending.
  Строка repayment/wrong-recipient до funding заблокирована конфликтом A-02.

### INV-20 — перестановочность погашений

- **Класс:** независимость от порядка, метаморфическое свойство.
- **Проверяемое свойство:** фиксированное множество применённых repayments даёт одинаковые status,
  Outcome, суммы, outstanding, exposure, counters и score во всех перестановках.
- **Минимальное состояние:** профинансированная сделка и два погашения с разными высотами.
- **Последовательность:** обязательные A(1100@110), B(1100@90) при face=1100,due=100; затем
  перестановки частичных сумм, переплат и платежей после закрытия.
- **Наблюдаемый оракул:** прямые суммы всех amount и on-time amount, насыщенный outstanding,
  каноническая классификация и полный пересчёт score/exposure.
- **Негативный контрпример:** первый полный поздний платёж фиксирует `PAID_LATE` и не позволяет
  последующему своевременному платежу уточнить до `PAID_ON_TIME`.

### INV-21 — атомарное совпадение статуса и итога

- **Класс:** свойство состояния.
- **Проверяемое свойство:** для каждого канонического Outcome статус сделки равен соответствующему
  paid/default статусу во всех наблюдаемых состояниях после вызова.
- **Минимальное состояние:** сделка на границе появления/уточнения итога.
- **Последовательность:** полное late/on-time погашение, default→paid, paidLate→paidOnTime;
  наблюдать сразу после каждого внешнего действия и при возможном revert.
- **Наблюдаемый оракул:** `canonicalOutcomeOf(dealId) == storedOutcome` и взаимно однозначное
  соответствие enum; при revert оба остаются прежними.
- **Негативный контрпример:** Deals записал `PAID_ON_TIME`, а Credit сохранил `PAID_LATE` либо вызов
  Credit не удался после уже сохранённого статуса.

### INV-22 — default только из FINANCED

- **Класс:** свойство переходов.
- **Проверяемое свойство:** даже при произвольно большой аттестованной высоте `markDefaulted`
  успешен только из `FINANCED`; `CREATED` и оба paid-статуса неизменны.
- **Минимальное состояние:** четыре сделки в `CREATED`, `FINANCED`, `PAID_LATE`, `PAID_ON_TIME`.
- **Последовательность:** поднять source height выше due+grace и вызвать default для каждой; повторить
  вызов для уже DEFAULTED.
- **Наблюдаемый оракул:** единственная разрешённая дуга `FINANCED → DEFAULTED`; только она создаёт
  default outcome/counter; reserve и exposure не меняются.
- **Негативный контрпример:** истечение срока дефолтит незапрошенную `CREATED` либо уже погашенную
  сделку.

## Абстрактная машина действий

Handler генерирует следующие действия, не повторяя ABI продукта:

1. создать обычную сделку для одного из нескольких заёмщиков;
2. создать предсказуемую сделку после заранее поданного unknown-deal evidence;
3. зарегистрировать корректный/ошибочный/частичный/нулевой/избыточный funding;
4. зарегистрировать repayment до funding, частями, с переплатой, разными source heights и неверным
   recipient;
5. повторить ID и отдельно повторить применение существующего evidence;
6. довести все pending evidence до неподвижной точки;
7. монотонно продвинуть аттестованную source height;
8. permissionless попытаться объявить default;
9. перемешивать несколько сделок одного заёмщика и несколько заёмщиков.

## Независимые оракулы

- **Суммы:** полный проход по применённым фактам; `repaidAmount` и `onTimeRepaid` не урезаются.
- **Outstanding:** `max(faceValue-repaidAmount,0)` без вычитания из переплаты.
- **Exposure:** полный проход по сделкам заёмщика в `FINANCED/DEFAULTED`.
- **Reserve:** полный проход по сделкам с активным резервом.
- **Outcome:** прямая классификация накопленных сумм, затем default при отсутствии полного погашения.
- **Counters:** полный проход по одному текущему Outcome каждой сделки.
- **Score:** отдельно из кеш-счётчиков и отдельно из полного прохода, в знаковой арифметике с одним
  итоговым clamp.
- **Available limit:** насыщенное вычитание из score-derived limit.
- **Evidence applicability:** existential oracle по неизменяемым полям и достижимым будущим
  состояниям; конфликтующая строка A-02 остаётся красной до решения спецификации.
- **Order independence:** сравнение полных снимков независимых экземпляров модели после одинакового
  мультимножества действий и доведения pending.

## Целевые регрессии

- Обязательный INV-20: `1100@110` и `1100@90` в обоих порядках → 2200/1100,
  `PAID_ON_TIME`, exposure 0, одинаковый score.
- Repayment до funding и после funding → одинаковый снимок после явного доведения pending (A-03).
- Частичные repayments в прямом/обратном порядке.
- Funding частями до порога; reserve переносится один раз; следующий funding — `ALREADY_FUNDED`.
- Три частичных fundings 60/50/40 в трёх порядках — исполняемое доказательство A-01.
- Default, затем поздно доставленный своевременный платёж → `PAID_ON_TIME`.
- `PAID_LATE → PAID_ON_TIME`; `PAID_ON_TIME` не понижается поздним платежом.
- Repayment после закрытия увеличивает полную сумму, но не освобождает exposure второй раз.
- Переплата насыщает outstanding на нуле.
- Default не освобождает exposure; падение score ниже used даёт available 0 без revert.
- Wrong recipient отдельно funding/repayment; до фиксации investor — сценарий A-02.
- Unknown deal остаётся pending, после создания повторно классифицируется.
- Два gateway events в одной транзакции → два ID (адаптер Verifier фазы B).
- ABI allowlist по всем селекторам, а не по списку подозрительных имён.

## Критерий подключения фазы B

Адаптер вправе только переводить реальные вызовы и чтения в уже определённые действия/снимки.
Менять формулы, ожидаемые переходы или исключать контрпример из-за поведения реализации запрещено.
Каждое расхождение сначала получает одну метку: ошибка реализации, противоречие спецификации или
ошибка модели. A-01…A-06 требуют отдельного решения до того, как соответствующая строка станет
обязательным зелёным тестом продукта.
