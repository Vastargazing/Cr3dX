# Проверка onboarding глазами нового разработчика

Дата: 2026-08-22. Ревизия до правок: `8a7dbdb` (`main`). Проверка локальная:
ключи, RPC и state-changing команды не использовались.

## Краткий вывод

Документация хорошо объясняет назначение продукта, модель доверия, отсутствие
привилегированных ролей и эксплуатационные риски live-сценариев. По комментариям
контрактов легко проверить ответственность каждого слоя. Локальные команды из
README воспроизводятся и дают заявленный baseline.

Главная сложность была не в нехватке информации, а в её маршрутизации. README,
workflow, спецификация, длинный status, runbook и исторические аудиты содержат
много правильных деталей, но до этой проверки не было короткого пути, который
объяснял бы новому разработчику, что читать сначала, а что является историческим
свидетельством.

## Что было понятно сразу

- продукт разделяет движение USDC в Sepolia и кредитное состояние в Creditcoin;
- `Gateway` только переводит токены и создаёт событие, `Verifier` принимает
  доказанный внешний факт, `Deals` классифицирует его, `Credit` хранит результат;
- Attestcoin является единственной связью между сетями, а worker отвечает за
  liveness и не получает доверенной роли;
- локальная сборка и тесты не требуют `.env`, ключей или сети;
- live-команды отделены от локальных и снабжены явными предупреждениями о
  транзакциях, изменении deployment ledger и восстановлении после сбоя.

## Где появились лишние шаги или сомнения

### 1. Не было короткого маршрута чтения

После README пришлось самостоятельно выбирать между большой спецификацией,
`STATUS` длиной более полутора тысяч строк, несколькими S6-документами и
историческими аудитами. Это не мешает найти ответ, но увеличивает время до первой
осмысленной правки.

Исправление: в README добавлен раздел `New contributor path`, который разделяет
product overview, нормативное поведение, текущий статус и исторические
свидетельства.

### 2. Историческое имя спецификации выглядит как устаревшая версия

Файл называется `cr3dx-spec-v0.4.0-final.md`, хотя действующая редакция внутри —
v0.4.8. Это объяснялось только внутри самого большого документа и в локальном
неотслеживаемом контексте.

Исправление: README теперь предупреждает об историческом имени до открытия файла.

### 3. Текущий статус в шапке спецификации был устаревшим

Шапка утверждала, что v0.4.8 ещё расходится с реализацией и только проверяется.
`docs/STATUS.md`, implementation-коммит, Phase B 63/63 и текущий deployment
фиксируют обратное. Поскольку workflow называет спецификацию главным источником
поведения, противоречие заставляло перепроверять историю.

Исправление: добавлена явно non-normative post-release-аннотация с датой,
implementation-коммитом и результатом Phase B. Рядом сохранено замороженное
нормативное основание: spec-коммит и SHA-256 входного пакета. Аннотация прямо
говорит, что появилась после проверки и не меняет поведенческие требования v0.4.8.
Исторические формулировки в журнале v0.4.8 оставлены как снимок document-only
этапа.

### 4. `forge` не находился в новом shell

Установленный Forge `1.7.1` находился в `~/.foundry/bin`, но директория не была в
`PATH`. Setup README содержит нужный `export`, однако минимальный checklist в
workflow начинался сразу с `forge --version`.

Исправление: одинаковая подсказка добавлена рядом с командами и в README, и в
workflow.

### 5. Полный тестовый цикл слишком дорог для первой итерации

Быстрые suites завершились сразу, а stateful invariants выполнили 896 000 handler
calls и долго не печатали прогресс. README честно предупреждал о паузе, но не
предлагал отдельную быструю петлю разработки.

Исправление: README теперь показывает быстрый Foundry-прогон без файла stateful
invariants и явно требует полный `npm test` перед handoff.

### 6. Предупреждение Forge о глобальном signature cache

В ограниченном окружении Forge не смог записать
`~/.foundry/cache/signatures`. Сборка и тесты при этом завершились успешно. Это
свойство контейнера, а не проекта, поэтому в публичную инструкцию оно не добавлено.

### 7. Каталог `personal/` не описывал назначение публичного логотипа

Отслеживаемый проектный логотип лежал в `personal/logo/`, хотя предыдущий cleanup
уже подтвердил, что это публичный проектный asset. Каталог перенесён в `assets/`,
а его назначение добавлено в repository layout. Исторический cleanup-report не
переписан: он сохраняет путь, существовавший в проверенном snapshot. Локальный
deck перемещён вместе с каталогом, но остаётся untracked и не входит в эту правку.

## Выполненная проверка

- `git submodule status`: оба submodule инициализированы на ожидаемых commit;
- Node.js `v22.22.1`, npm `9.2.0`, Forge `1.7.1`;
- `npm run typecheck`: успех;
- `npm run test:scripts`: 10/10 suites;
- `npm run build`: успех;
- `npm test`: 141/141 tests, включая 8/8 invariant/property suites;
- быстрый `forge test --no-match-path 'test/Cr3dXInvariants.t.sol'`: успех.

## Что ещё помогло бы в будущем

Если проект станет больше, следующий полезный шаг — сделать одну локальную команду
вроде `npm run check:quick`, которая объединит быстрый Foundry-прогон, TypeScript
tests и typecheck. Пока точные команды в README достаточны и не добавляют новый
слой tooling.
